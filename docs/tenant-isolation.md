# Tenant isolation implementation and release boundaries

This implementation is not qualified for production or 1,000 concurrent users. The Mac-only PR16 is separate. Production startup requires an explicit `SWARM_ROLE`: the existing shared service sets `SWARM_ROLE=standalone` (see `fly.toml`), and the isolated platform uses the other roles; a process whose role is unset is refused so a tenant image never starts as a shared server by accident. Migration is not wired to production adapters.

## Deployment model

Each immutable Swarm account owns one Fly application, private network, microVM and encrypted volume. That environment supports multiple Bots, windows and concurrent subscription requests. Platform operators, the Fly hypervisor and upstream providers remain trusted boundaries.

| Role | Responsibility | Credentials and storage |
| --- | --- | --- |
| `platform` | Provider sign-in, sessions, routing, phone/messaging ownership, encrypted events, host backup API | PostgreSQL metadata, platform signing key, OAuth/messaging credentials, KMS and scoped backup access |
| `provisioner` | Durable lifecycle, reviewed recovery/image replacement, backup/volume retention | PostgreSQL, staging/production-specific Fly token, KMS, backup storage; no conversations |
| `composio-gateway` | Narrow connection and tool API; callbacks and triggers | Platform-owned Composio project credential, PostgreSQL, runtime verification public key, event encryption access |
| tenant host | Verify release/volume identity, renew runtime identity, supervise containers and backups | Root-only bootstrap/refresh and host token, only this tenant's data key and volume |
| `tenant` | One account's application, SQLite WAL, files, Bots, approvals, MCP and durable jobs | Tenant data key and runtime token; no platform database, Fly, Composio or AWS credential |
| `standalone` | The existing single shared server (legacy boot path), local development and compatibility tests | Shared process; not per-user isolation and never counts toward isolation qualification. Allowed in production only when `SWARM_ROLE=standalone` is set explicitly |

`server/src/index.ts` loads only the selected application role. The tenant database owner, configured immutable ID and volume manifest must agree. The tenant application's server accepts routed requests carrying short-lived signed authorization. Incoming browser identity headers are stripped at the platform; they cannot choose a tenant or VM.

The host creates separate application, desktop, subscription and local MCP containers. Workloads are non-root, have read-only roots, private temporary directories, dropped capabilities, no-new-privileges and process/CPU/memory limits. They receive no Docker socket or host key directory. Subscription containers mount only the selected provider home; MCP containers get an empty workspace and their own configured environment. Users may explicitly share up to eight Library folders with a local MCP server, read-only, at `/workspace/folders/1` through `/workspace/folders/8`. The folder picker and save path check the owning Bot. Absolute paths, traversal, symlinks, overlapping grants and remote-server mounts are rejected; browser profiles, runner homes and the database are outside the eligible file root.

Folder grants are stored in the encrypted connection configuration and covered by its revision. Changes clear discovery and prior approvals, and close cached sessions, pending handshakes and connection tests. Credential changes and folder grants require recent authentication, rechecked after reading the request body. Migration and backup recovery clear folder grants for explicit review. The host reopens each directory with no-follow descriptor-relative resolution, holds its descriptor while creating a private nonrecursive bind, and remounts it read-only/nosuid/nodev/noexec. Docker receives only root-owned staged paths with recursive binds disabled. Cancellation waits for mount preparation and confirmed container removal; failed cleanup retains ownership for retry, closes admission and signals host shutdown. Real kernel/Docker mount semantics remain a staging gate; mocked mount-driver tests do not qualify them.

Images are embedded in a signed host release and selected by immutable digest. Boot does not install remote executable code. The build verifies component signatures and scans high/critical findings; publishing and signing the final host image still require an operational release pipeline. Docker's default seccomp policy is used and must pass the actual containment tests for the release kernel/images.

Host startup runs a networkless canary before credential registration and verifies actual kernel cgroup, seccomp, non-root, capability and read-only-root enforcement. Docker reporting that a flag is supported is insufficient. Firewall setup is mandatory before readiness. It blocks private/reserved/metadata and cross-container destinations, with a single desktop-to-app exception; IPv6 forwarding is denied. No Fly public services are configured for tenant VMs. Separate Fly applications alone are not proof of separate networks: the provider response must attest the requested network. Failure stops provisioning.

Hosts authenticate while held and start workloads only after a persisted `run` policy for their exact tenant, machine and runtime generation. A policy revision becomes ready only after the host verifies application health and SQLite ownership and acknowledges it. Browser routing and active relays require a recent matching acknowledgement. Holds revoke runtime tool authorization; the host polls policy and stops on authorization loss. Full backups mark readiness held while workloads are stopped.

The provisioner uses fenced leases, one active lifecycle operation per tenant and durable cloud-creation intents. A lost create response is resolved by inspecting owned resources; an absent result does not authorize a second create. Deletion inventories the deterministic tenant namespace even when a late resource never reached directory metadata, stops discovered compute and remains pending while any creation outcome is unresolved. Suspension stops the machine. Wake installs fresh credentials into a stopped machine, including after refresh expiry, and requires new readiness. The root refresh journal binds tenant/machine/volume/generation and preserves pending exchanges and consumed-bootstrap hashes across restart. Config-file replay cannot replace a valid refresh with a consumed bootstrap. Provider API semantics and these stop/start races still require staging qualification.

Runtime companion registration and encrypted event reads/acknowledgements recheck signed identity, expiry, machine, generation and the host run permit under the same tenant lock used by lifecycle changes. Authorization is read in a fresh statement after acquiring that lock, avoiding a stale policy snapshot. A request admitted before revocation cannot mutate metadata after waiting on its body or the lock. Messaging also rechecks runtime authority when reserving a dispatch, issuing a login token/invite or disconnecting a route, and immediately before provider dispatch, including after media upload. Work already issued to a provider may still have an uncertain outcome and is never blindly replayed.

## Identity and sessions

Google uses OIDC signature/issuer/audience/nonce verification and verified identity claims. Apple and OpenRouter use their verified provider identities. No provider identity is joined using an email string. Adding another provider requires an authenticated linking flow; mutable email/phone settings do not confer administrator privileges. Platform roles use immutable account IDs. Development sign-in is refused in production. No passkey requirement is introduced.

Sessions are random opaque tokens stored as hashes, rotated on login, with seven-day absolute and 24-hour idle limits. Cookies are Secure, HttpOnly and host-only. Identity linking, credential changes and deletion require recent authentication. Native handoffs exchange short-lived, single-use PKCE-bound codes; persistent session credentials are not placed in URLs. The legacy cookie alias is supported only by standalone compatibility, never tenant authentication.

The browser's platform cookie never enters a tenant VM. HTTP and viewer relays derive a separate cookie using HMAC over the immutable tenant, runtime generation and platform session hash. All platform replicas must share the same stable `SESSION_SECRET` (at least 32 bytes); it must never be copied to a tenant. A `tenant_sessions` directory record maps the delegated hash to the original live platform session for narrowly scoped Composio authorization attempts. The delegated cookie cannot authenticate to platform account or administrator routes. Foreign tenants, old generations and revoked/expired sessions cannot resolve that mapping. Deleting a platform session cascades to its delegated mappings. The provisioner prunes expired/idle sessions and old-generation mappings in bounded batches, skipping rows held by active transactions.

Relays register pending work before body/signing waits and repeat session, generation and host-readiness checks before dispatch. Single-session revocation translates to the delegated hash, closes pending/active relays and revokes the imported tenant session. Native pairing rechecks owner, scope, generation and host readiness after signing. Relayed documents receive a sandbox CSP so a compromised tenant cannot serve an active same-origin page. PostgreSQL commit notifications now propagate session, native-pairing and tenant/host-policy revocations to every platform replica. Each replica reserves a dedicated LISTEN connection, verifies that the required directory triggers are enabled before readiness, and closes all relays and returns health 503 if notification continuity is lost. Reconnection permits only fresh authoritative checks; it does not resume cancelled work. A 15-second query remains a fallback for expiration and runtime liveness. Real PostgreSQL tests cover two replicas, transaction rollback, scope/owner separation and backend termination; production failover and latency still require qualification. Use direct PostgreSQL or session pooling, never transaction pooling, for the listener.

Authorization is rechecked after blocking operations and before credential side effects. Revoked CLI terminals and sessions are closed; account deletion rechecks authorization inside the credential mutation lock. Platform native linking, deletion and delayed credential events recheck the initiating session transactionally. WebSocket/viewer routing is bound to owner, session, Bot and permitted control mode. Existing Mac consent and computer-revision guards are retained.

## Subscription and provider credentials

Claude and Codex use the account holder's own subscription credentials. Independent subscription Bots and helpers overlap without an application generation cap, account queue or helper-count cap. The same Bot keeps history ordering. Login/disconnect remain exclusive credential mutations, and each container retains its resource limits. Provider allowances and the finite VM still apply; concurrency is not a capacity guarantee.

Errors, exhausted subscriptions, missing authentication and disconnections stop work. Switching to an API provider requires an explicit selection. Tenant execution never falls back to another account, an operator subscription or a platform model/voice key. Voice needs a compatible private credential. An optional personal-computer bridge retains its own consent/authentication boundary.

KMS creates one data-encryption key per tenant, using tenant-bound encryption context. Secret envelopes bind owner and purpose; MCP OAuth secrets also bind configuration revision. The platform project key never enters a tenant VM or browser. File credentials inside subscription containers are protected by isolated encrypted storage and encrypted backups rather than application-level encryption while the official CLI uses them.

Composio mapping is `immutable tenant → private Composio user identity → specific connected account`. Every supported operation verifies local and upstream ownership. Multiple accounts require an explicit selection or saved default. Models cannot override user/account identity or use project administration, arbitrary authenticated proxying or an unrestricted workbench. Dispatch IDs persist completed or uncertain outcomes; unknown external writes are not blindly repeated. Revocation blocks subsequent dispatch. Existing issued upstream actions cannot necessarily be undone.

Remote MCP uses HTTPS, destination validation on the actual connection path, private/reserved/IPv6/rebinding defenses, bounded responses and no credential-bearing redirect following. OAuth uses PKCE and resource/audience validation. Private-network endpoints are disabled. Local stdio commands go through the host supervisor only; there is no shared-process fallback. MCP tools/results/metadata remain untrusted data. Sampling, unsolicited elicitation and executable extensions are disabled.

MCP ownership covers tenant, Bot, connection, revision and permission. New connections default to no Bots and require approvals. Configuration/revision changes invalidate discovery, sessions and approvals. Initial limits are 20 connections, 1,000 tools per connection (4,096 assigned per Bot), 12-second handshakes, 60-second calls and five-minute idle cleanup. Foreign IDs have the same not-found behavior as unknown IDs.

## Messaging and durable work

The platform verifies signed incoming events and derives destinations from private phone/channel records. Phone challenge consumption, invitations and identity admission are transactional. Linking codes require the initiating recent session. Web login links are single-use and become invalid on disconnect; session issuance and token consumption share a transaction. Messaging `/delete confirm` revokes the platform account and queues cleanup.

Routes keep increasing revisions through disconnect/reconnect. Durable receipts prevent a webhook replay from re-enqueuing after its wake event was acknowledged. Message content awaiting a VM is encrypted for that tenant. Both runtime event ingestion and the durable messaging inbox check the route/revision. Authentication outages remain retryable; revoked or malformed events are retained encrypted for reconciliation. Event acknowledgements follow committed durable work, so a lost response and process restart do not apply the same event twice.

Audio accepts bounded bytes rather than arbitrary caller URLs. Upload and send do not follow redirects; disconnect during upload prevents the subsequent send. Typing and replies use only the owner's stored conversation. Uncertain sends are recorded, not automatically retried.

Tenant jobs survive process restarts. Interrupted external actions may require reconciliation. Phone verification, invitations, native linking, audio/typing, deletion and signup administration have deterministic coverage. Live native/messaging provider compatibility remains a release gate.

Platform phone/messaging signup policy, administrator invitations and waitlist controls now live in the platform directory. Administrator access requires an explicit `account_roles` entry for an immutable account ID, a live browser session and recent authentication for changes. A tenant runtime, matching email or tenant database owner flag cannot confer this role. Ordinary users see only their own member invitation. Policy and waitlist changes carry expected revisions; checks repeat after lock/body waits. See [signup administration operations](platform-signup-operations.md) for initial role assignment, defaults, retention and fresh phone-proof semantics. Existing standalone owner controls remain separate.

## Backups, retention and recovery

The root host schedules database snapshots every four minutes and full environment snapshots every 23 hours. SQLite uses its online backup API. A full environment backup stops the supervisor/application/desktop, verifies quiescence, captures files/profiles, then restarts them. This interrupts active work; the restart and uncertain-job experience must be qualified with real workloads.

Bundles have tenant-bound authenticated encryption, checksums and an encrypted inventory. Root-owned journals resume uploads after restart. Orphaned local bundles are cleaned without following symlinks. A host-audience JWT authorizes backup transport; an application runtime JWT cannot upload/list through that API. S3 keys are derived by the platform from tenant, backup ID and validated part name. Platform S3 credentials never enter a tenant VM.

Every ordinary backup part has an exclusive upload token and a three-minute outstanding-write lease. Dispatch is bounded to two minutes and independently verifies the complete byte count/checksum and stream consumption. Authorization is checked after database lock waits, during streaming and before acknowledgement. Failed or lost responses retain the lease; cleanup waits for it and an older request cannot release or downgrade its successor. Host retries keep the same encrypted bundle until the outstanding attempt expires. Real S3 abort/eventual-write behavior remains a qualification gate.

Configure `BACKUP_BUCKET`, optional `BACKUP_PREFIX` (default `swarm-backups`), `AWS_REGION`, and short-lived IAM via the SDK chain. Grant required S3 get/put/delete/version/multipart actions only within the dedicated prefix, with bucket-list conditions for that prefix. Deny public access and insecure transport. Retention deletes historical object versions, delete markers and abandoned multipart uploads. An S3 lifecycle rule must also expire aborted uploads and orphaned objects; set its retention consistently with the application catalog and disaster-recovery policy. Object Lock/legal holds would block deletion and must be explicitly reconciled.

Database snapshots expire after one hour; full environments after seven days. Failed deletion remains visible and retries. Account deletion waits for backup cleanup before destroying its tenant key. The bucket and PostgreSQL need independent operational recovery policies; this code does not configure managed PostgreSQL PITR.

`BackupCatalog.health()` exposes metadata-only reporter age, database/profile age and retry state from host reports. Alerts should fire on a reporter older than three minutes, DB snapshot age over five minutes, full environment age over 24 hours, or failed cleanup. Wiring this to the production alert destination remains an operational task.

`restoreTenantEnvironment` checks owner, catalog completeness, checksums, authenticated inventory, DB integrity and runtime generation, and restores into a new unpublished directory. A newer DB snapshot may overlay a full backup. Sessions/pairings/OAuth attempts are cleared. A recovery receipt is published last and records `routingChanged:false`; incomplete destinations without that receipt must never be activated. Platform routing cutover and VM replacement are separate fenced operations.

`stageHostInstallation` and the host installation API implement the encrypted transfer boundary. A trusted migration/recovery transaction reserves immutable backup IDs for a held, unpublished tenant/machine/volume/generation. Only that host's JWT can read those parts; tenant workload tokens and foreign hosts cannot. Responses are bounded and checked for ownership, size and checksums. The host decrypts and validates a full backup plus an optional newer database, durably publishes a new private environment directory and pointer, then acknowledges completion. Startup is prohibited while installation is pending. A lost acknowledgement retries without overwriting published data; missing acknowledged data fails startup. S3 credentials remain on the platform. Retention preserves admitted pending restore inputs; account deletion overrides the hold.

Recovery marks queued/running jobs, pending incoming messages and queued/sending replies uncertain, and denies pending approvals. It disables recovered native-computer consent and MCP Bot permissions, clears MCP discovery/OAuth and requires explicit reconnection/review. A snapshot can predate an external action or revocation, so recovery cannot safely replay work or reactivate old grants. This differs from an ordinary process restart using the current durable database.

`environment-cli` and `EnvironmentWorker` now connect recovery and image updates to the Fly driver and host protocol. A read-only plan names the exact source binding, image and backups; explicit queueing rechecks that binding and qualified image before revoking the old runtime generation. The worker verifies source stop/removal, restores to a new encrypted volume (or retains the current volume for an image update), issues new bootstrap credentials and waits for installation/readiness before routing. Durable leases and creation intents protect retries. Before any target run permit, explicit rollback can recreate the preserved source with fresh credentials. After a run permit, rollback requires current data or a reconciled checkpoint. Old restore volumes receive seven-day retention with confirmed, scoped cleanup. See [operator commands and recovery procedure](tenant-recovery-operations.md). This is implemented for already isolated accounts and tested with simulated infrastructure; legacy source migration remains unfinished.

No real S3/KMS restore or RPO/RTO drill has passed. Temporary snapshot/encrypted-bundle space competes with user data on the proposed 10 GB volume. Actual usable storage, backup I/O, interruption duration and recovery time need measurement; the initial volume size is not a proven storage budget.

## Migration and deletion

The following are offline trusted operator libraries, not browser or agent APIs:

- `stageLegacyImport` checks an audited frozen snapshot and explicitly selected provider-subject bindings. It reserves the old immutable tenant ID without provisioning it. Only a fresh verified provider callback redeems the corresponding claim. Equal email strings cannot claim an import. Each imported Composio account must be attested as private under the original immutable user identity; unproven accounts require reconnection. Do not approve historical bindings whose provenance is ambiguous.
- `prepareMigrationPackage` exports only proven owned records, including hidden Bots and relationships; rejects unknown ownership, cross-owner joins, symlinks, hard links and changed files; and inventories file hashes. Only authenticated owner-bound credentials are rewrapped. Ambiguous shared legacy credentials require reconnection. MCPs are disabled and permissions/approvals reset. Receipts identify missing inventories and verification gates.
- `planMigrationDestination` and `MigrationDestination.reserve` bind a reviewed region/image to the exact held export and reserve only its private Fly app/network and encrypted volume. Creation intents prevent blind retries; missing or unexpected resources require reconciliation. Revocation, expired leases and source changes prevent publication. Reservation creates no VM, credentials or run permit; the account remains pending. Real Fly semantics remain unqualified.
- `MigrationTransfer` binds that packager to a complete source checkpoint, reserved destination, current migration lease, tenant KMS key and one immutable encrypted upload inventory. Private workspace/journal ownership checks prevent source/tenant substitution; lost responses resume identical ciphertext after outstanding upload leases expire. Revocation/source/destination changes prevent publication and trigger source containment where authorized. The existing host installer consumes the transferred owner-only bundle, including empty files, and rejects mismatched source checkpoints/fences regardless of backup expiry. Transfer never enables routing or claims that a partial drain is a full source freeze.
- `MigrationCoordinator.beginExport` reserves the immutable operation, refuses any prior generic provisioning attempt and obtains a full source freeze before an export package can be accepted. The `exporting` phase has no target package or authorized writer. `prepare` verifies the package against that exact still-held checkpoint; `cutover` rechecks the same source fence. Lost freeze responses, partial database-only receipts and a resumed source require containment/reconciliation. The coordinator persists leases and single-writer state, inspects uncertain activation, and attempts to fence both writers after failure. Rollback requires a reconciled checkpoint and avoids overwriting a resumed source after a crash.
- `FlyMigrationTarget` now connects target creation, held installation, bootstrap, run permit and readiness to that coordinator. Dispatch authorization follows the Fly driver's own lookups. Root-only fresh checkpoints run on a held boot after observed target stop, capture the current encrypted database/files/profiles, and require another observed stop before source restore. The original imported package cannot serve as a post-activation rollback checkpoint. Lost starts and missing journals require reconciliation. This adapter is implemented with synthetic infrastructure integration tests; real Fly/kernel/source qualification remains required.

The legacy database portion now has a concrete maintenance primitive, `holdLegacyDatabase`, with durable account/operation/monotonic-fence records and SQLite triggers. It covers direct and inherited ownership, hidden Bots, room membership, phone events and OAuth session references. Late writers on another connection are blocked, including `REPLACE` conflicts through rowid or uniquely collated indexes. Unmapped tables/indexes are refused atomically. Startup refuses schema drift or missing/changed guards; frozen accounts cannot authenticate through existing sessions. The encrypted export omits the legacy hold records/triggers and validates implicit room/helper/preference/usage relationships in both directions.

`withUsage` also tracks in-flight work without serializing it. A held account cannot admit more tracked work, and a bounded drain reports only when its tracked callbacks settle; another account can continue independently. **Neither this drain nor the database hold proves file, VM or subprocess quiescence.** Their receipts explicitly identify the limited boundary and cannot satisfy a migration source checkpoint. There is no public freeze/release endpoint or enabled production source adapter. Do not apply a hold to a real account until process/file fencing and reconciled rollback are wired and qualified. This mechanism assumes trusted legacy application SQL; it does not protect against an operator or process that can disable/drop SQLite triggers.

The legacy source now also has concrete current-process and desktop drain functions. Background provisioning, inbox, message, subscription and MCP admission honors the durable hold; late VM creations remain reserved for reconciliation. Owner streams are disconnected, login/subscription work cancelled under the credential lock and tracked callbacks drained while preserving credentials. The desktop stopper verifies exact provider ownership and observes `stopped`, with authorization rechecks after waits. These functions explicitly report `current-process-only` and `legacy-desktop-only`; neither proves filesystem quiescence. See [legacy migration implementation boundaries](legacy-migration-implementation.md).

**Unfinished deployment integration:** the complete legacy source freeze/inspect/restore/resume/retirement adapter and maintenance entrypoint remain unimplemented. Target reservation, transfer, activation/stop and fresh-checkpoint adapters now exist, but are not production-qualified or enabled for real migration. The source contract requires persisted operations, monotonically enforced fencing, actual filesystem/process quiescence and safe reverse credential rewrap. These libraries are not an end-to-end production migration command. Audit a real snapshot and host inventory, implement/qualify the source, prove one writer, and complete actual infrastructure cutover/rollback/deletion drills before migrating real credentials.

Ordinary isolated-account deletion revokes sessions, runtime generation, provider connections and routing before retryable cleanup. Provisioning cannot wake a deleted tenant. Provider disconnection, backup cleanup, VM/volume destruction and key deletion are durable prerequisites; unresolved cleanup must remain visible. Migrated accounts additionally require an actual source-retirement digest/timestamp: merely stopping legacy writers cannot satisfy deletion. That retirement adapter, operator runbook and real evidence remain unfinished.

## Validation and qualification

Run against disposable local PostgreSQL:

```sh
npm ci
npm run typecheck
npm run build
TEST_DATABASE_URL=postgresql://user@127.0.0.1:5432/isolation_test npm run test:isolation
npm run test:cli
```

`test:isolation` refuses a missing PostgreSQL URL. It includes identity/session, MCP, simulated Composio ownership, messaging, migration, storage, event delivery and relay tests. `.github/workflows/isolation.yml` runs it against a disposable database. These are deterministic tests; 50 Notion and 150 Gmail fixture authorizations are not live-provider evidence.

On a qualified disposable host only, supply an already-pulled immutable shell-capable test image and run:

```sh
RUN_CONTAINER_TESTS=1 CONTAINMENT_TEST_IMAGE=sha256:IMAGE_CONFIG_DIGEST node --import tsx --test tests/container-containment.test.mts
```

Do not run this command with a placeholder digest. The current cloud workspace cannot start containers with the required cgroup domain controls; those attempts failed and are not passes. Do not disable limits, seccomp or Chrome sandboxing to obtain a green result.

The [bounded qualification plan](tenant-qualification.md) specifies actual staging prerequisites. Required release evidence includes signed/scanned images, Fly private-network/volume behavior, live subscription support and provider authorizations, containment and compromised-tenant testing, backup/recovery/deletion drills, independent security assessment and production alerting/abort controls.

The initial capacity hypothesis is 1,000 users actively running one Bot each, 2 shared vCPUs/4 GiB/10 GB per VM, with separate platform capacity and 25% headroom. It is not a measured result. Test subscription overlap/helpers without adding the account queues the owner explicitly rejected. After bounded qualification, obtain approved quotas/budget and ramp through 25, 100, 250, 500 and 1,000 active users, a 1,250-user burst and 24-hour soak, at 0/10/100% desktop viewing. Required gates include zero cross-user access, no high/critical findings, control API p95 below 500 ms, warm admitted tasks below two seconds p95, fewer than 1% platform errors, durable jobs and bounded resource growth. Any cross-user exposure halts rollout.
