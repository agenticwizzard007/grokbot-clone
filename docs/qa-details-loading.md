# Details, voice polling and loading QA

Local investigation of QA items 11 through 15, originally reported on 561fcc9. No live sign-in or real account data was used. The work includes voice setup PR #187 and builds on catalog PR #188 and cancellation PR #189.

## Findings and changes

- 11: The redesigned Details workflow card did not inherit the earlier identity wrapping rules. Long names also escaped Routines helper text, and General retained a save bar with negative margins wider than the phone column. These now wrap within their containers. The extended I08 identity browser test measures scrollWidth/clientWidth and actual text line rectangles across all Details tabs and Bot settings at 390, 768, 1024, 1280 and 1440.
- 12: POST /api/voice/updates is mounted by the production API. Its JSON 404 means the in-memory, account-bound call no longer exists or its conversation generation changed. A deployment/restart can also discard this state. The client treated this as a transient error and polled every 1.5 seconds indefinitely. Terminal 401/403/404/410 responses now end the local call with Retry. Temporary failures preserve the last task snapshot, use a four-second deadline and exponential backoff up to 30 seconds. End, pagehide and call UI unmount stop timers and abort requests. Setup timing and microphone permission reuse remain covered by #187's tests.
- 13: Analytics omitted the description above the tabs; other descriptions and the tab-dependent page title could wrap to different heights. The existing scrollbar gutter was already stable. The Bot name now forms the stable heading and the description follows the navigation. Learning flags use SettingRow with 20px icons, label/helper text and trailing controls, 16px gaps and four pixels between label/helper. Expanded number fields align icons with labels too.
- 14, suggestions: Catalog discovery, model discovery/ranking and current connection lookup were sequential, with nested 6/8/10-second server deadlines and a 12-second browser deadline. Suggestions now reuse #188's catalog cache, use the ranker's conservative input budget without another model discovery request, allow 1.5 seconds for ranking with a catalog-only fallback, and bound the full route at four seconds. The existing catalog cache now bounds a cold read at 3.5 seconds; the client uses 4.5 seconds. Account-scoped suggestion responses use #188's shared settings cache primitive, retain previous results during refresh and provide Retry on failure. No second toolkit catalog cache was added.
- 14, usage: The widget waited for /api/models, which forced CLI catalog discovery with a 23-second transport limit or reverified the direct key on every request. Passive CLI reads now reuse the existing account/runtime TTL and revalidate stale metadata in the background with a 3.5-second deadline. Direct metadata has a bounded account/configuration-scoped TTL cache. The browser ends loading within five seconds and keeps a display-only, account-scoped summary across reloads, marked Previously loaded. Old quota percentages still expire under the existing 30-second freshness rule. Retry remains available.
- 14, Tasks: The roster read had no deadline and its server handler hydrated the same Bots and previews twice. The duplicate work is removed and Server-Timing is emitted. Roster, task and attention reads have four-second deadlines and retain already loaded data on failure. Tasks is preloaded after the initial shell render. A failed dynamic import retries a same-origin module URL once with a fresh query, because browsers can cache module failures. A 4.5-second deadline displays Unavailable with Retry for persistent failures, without reloading the document.
- 15: AppRow has no selection checkbox. Google Tasks metadata artwork can resemble one. That toolkit now uses the existing standard letter avatar, including the google_tasks slug alias. Local search tests assert one logo, a G avatar and no checkbox artwork/control.

## Events and Fly review

The existing SSE handler writes complete frames, flushes an initial hello, sends data heartbeats every ten seconds, disables compression/buffering and omits HTTP/1-only headers. Local HTTP/1 and HTTP/2 tests verify those headers and heartbeats. The client uses one EventSource, closes failed streams, revalidates the session with a five-second limit, reconnects with bounded backoff and has a 45-second silent-stream watchdog. Roster requests and the Tasks import do not await the stream. The client previously reset backoff on every accepted connection, allowing repeated immediate protocol resets to reconnect every second. It now resets backoff only after ten seconds of valid delivery. Local tests cover repeated hello/reset cycles, heartbeat recovery and concurrent roster requests over both HTTP/1 and HTTP/2. No run cancellation or event ordering logic was changed.

fly.toml has no h2_backend override, so Fly terminates public HTTP/2 and uses the normal HTTP/1 backend. There is no explicit proxy idle-timeout or concurrency setting. The health check is GET /api/health every 30 seconds with a five-second timeout and a 20-second grace period. The always-on machine is shared-cpu-1x with 1 GB RAM. This is a capacity concern for a shared application serving SQLite, SSE, provider metadata and hosted CLI processes together; measure CPU, RSS, event-loop delay and connection count under load before choosing new limits or capacity. No paid machine size, billing, autoscaling or deployment workflow was changed.

The reported production HTTP/2 ping/protocol errors cannot be attributed to a specific Fly failure from repository inspection and local fixtures. No Fly logs or production account access were available. Local deadlines and retry states prevent those transport failures from holding the UI in loading indefinitely.
