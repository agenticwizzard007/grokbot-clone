# Multitenant owner steps

## MT-E: Tenant isolation proof matrix

MT-E's [local evidence](tenant-isolation-evidence.md) needs no external account or secret. The following steps are for later real qualification and were **not run**. Unknown account IDs, keys, domains and digests must come from the owner's approved inventory, never from a fabricated fixture.

1. Approve a dedicated staging inventory: `FLY_ORG_SLUG`, two isolated test tenant IDs, platform/gateway HTTPS origins, region, disposable apps/volumes, spend and retention limits. Follow [staging bootstrap](../infra/platform/staging-bootstrap.md). Keep `SWARM_ROLE=standalone` on the existing shared deployment. Resolve the initial qualification-bootstrap dependency in that runbook's step 9 before creating tenant inventory; never insert passing gates or enable ordinary provisioning to bypass it.
2. Supply staging AWS resources through a protected file outside the repository: `TENANT_KMS_KEY_ID` (symmetric KMS key ARN), `AWS_REGION`, `BACKUP_BUCKET` (private, versioned S3 bucket), `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` for the restricted application principal. KMS encryption context must be `{tenant: <actual tenant ID>, purpose: "swarm-tenant-master-v1"}`. Run the exact generate/decrypt-only restricted-principal probe in staging-bootstrap step 0b. Require 32 bytes, same-tenant equality, `InvalidCiphertextException` for a foreign tenant context and `AccessDeniedException` for wrong purpose. An administrator verifier alone is insufficient. Verify S3 denial outside `swarm-backups/` with the same restricted principal and archive sanitized results and principal/key provenance.
3. Supply a separate Composio staging project through protected files: `COMPOSIO_API_KEY` and `COMPOSIO_WEBHOOK_SECRET`. Configure its webhook at `${COMPOSIO_GATEWAY_URL}/webhooks/composio`; use the actual connect callback generated by the platform, not a fixture URL. Provide private test accounts A1/A2 for tenant A and B1 for tenant B for each tested toolkit, with disjoint disposable data. Follow [provider qualification](provider-qualification.md) for read-only probes, callback-session refusal and exact evidence requirements.
4. Supply staging `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`; register exactly `${PLATFORM_URL}/api/auth/google/callback`. Keep `PLATFORM_URL`, `APP_URL` and `SERVER_URL` on the approved platform HTTPS origin. Supply the staging-only Inkbox line and `INKBOX_API_KEY`, `INKBOX_ADMIN_API_KEY`, `INKBOX_IDENTITY_ID`, `INKBOX_SIGNING_KEY`, `INKBOX_HANDLE` as specified by the deployment runbook. Configure inbound delivery at `${PLATFORM_URL}/api/messaging/inkbox/webhook`. Real provider compatibility, test identity login and any message-producing drill need their own approved inventory and execution authorization; MT-E sends none.
5. Obtain a reviewed, scanned and signed exact `TENANT_HOST_IMAGE` digest and the associated provenance. Run the [real containment qualification](../infra/tenant-host/qualification/README.md) without changing seccomp, Chrome sandbox, roots, firewall or capabilities. Separately prove two-app network separation and real A-to-B credential/viewer/provider refusal. Run WS7 backup/restore/deletion drills against the approved S3/KMS resources, including versions, multipart remnants, key destruction and the required recovery objectives.
6. Archive actual sanitized artifacts with source SHA, host digest, command, creation inventory, timestamps and artifact SHA-256. An authorized operator records real artifacts through `release-gates-cli record`; an independent reviewer approves only substantiated evidence. Require `release-gates-cli verify <exact-image@sha256:...>` for `fly-network-isolation`, `nested-container-containment`, `signed-runtime-image`, `provider-hosted-login` and `provider-quotas` before ordinary provisioning. This local matrix is not an input that can approve any of those gates.
