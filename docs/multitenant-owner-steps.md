# Multi-tenant owner steps

## MT-A: Dockerized platform stack

Local Docker bootstrap requires no owner-held accounts or secrets. The following steps are required before using the same application image with real services; they were not executed by MT-A.

1. Provision a dedicated PostgreSQL database with `directory_owner` and `app_runtime` as in `infra/platform/staging-bootstrap.md`, sections 1 and 6a. Set `MIGRATION_DATABASE_URL` only on the one-shot job and `DATABASE_URL` only on trusted platform services. Use direct or session-pooled connections with TLS. Confirm runtime cannot create tables and receives LISTEN notifications.
2. Create the reviewed symmetric AWS KMS key and restricted principal using the AWS setup runbook. Set `TENANT_KMS_KEY_ID` to its ARN and `AWS_REGION` to its region. Supply AWS credentials through the SDK chain to platform, provisioner and gateway. Remove `TENANT_KMS_ENDPOINT` and all local emulator credentials. Prove generate/decrypt context restrictions with the real restricted principal before admission.
3. Create the private versioned backup bucket, prefix, lifecycle and incomplete-upload expiry policy. Set `BACKUP_BUCKET` and `BACKUP_PREFIX` on platform and provisioner. For AWS S3 omit endpoint overrides. For a reviewed Tigris or other S3-compatible service set `BACKUP_S3_ENDPOINT=https://<provider endpoint>`, `BACKUP_S3_REGION=<provider region>`, the provider's required `BACKUP_S3_FORCE_PATH_STYLE`, and separate `BACKUP_S3_ACCESS_KEY_ID`/`BACKUP_S3_SECRET_ACCESS_KEY` (optional `BACKUP_S3_SESSION_TOKEN`). Production overrides also require the deliberate setting `SWARM_ALLOW_LOCAL_CLOUD=1`. Never place object storage credentials in the AWS variables used for KMS. Qualify version deletion, multipart abort and restricted-prefix access with the real provider.
4. Generate a separate production Ed25519 pair offline with `scripts/platform-keys.sh /secure/swarm-production/keys`. Mount the private PEM only on platform at `PLATFORM_PRIVATE_KEY_FILE`; mount the public PEM on platform and gateway at `PLATFORM_PUBLIC_KEY_FILE`. Fly file secrets require base64-encoded PEM input. Do not reuse local emulator keys or the local session secret.
5. Supply the dedicated Composio project credential and webhook secret to gateway, and configure the real project/callback ownership according to the platform runbook. Supply the Google OAuth client through `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` on platform; register exactly `${PLATFORM_URL}/api/auth/google/callback`. Set owned HTTPS platform/gateway origins and their required DNS/certificate records. Local Caddy certificates are development-only.
6. For Fly, provide the dedicated staging organization and scoped driver token, publish the qualified tenant host digest and archive real qualification evidence through the existing tooling. Use the same reviewed role-image digest for the platform, provisioner, gateway and migration job with their existing Fly manifests. Do not deploy the live shared-server manifest. Omit `SWARM_LOCAL_PROVISIONER_HOLD` in production; missing evidence must still refuse provisioning. A Docker tenant driver deployment must follow its own reviewed supervisor and socket boundary. MT-A grants no Docker socket access and does not qualify that boundary.

## MT-B: Docker tenant driver

No external account, secret or DNS record is needed to build or run the fake-engine tests. To use Docker staging, the owner or operator must provide a dedicated Linux host whose Docker `/info` reports `MemoryLimit`, `SwapLimit`, `CpuCfsQuota` and `PidsLimit` as true and includes `name=seccomp,profile=builtin`. The current development sandbox lacks swap-limit enforcement; run the real two-tenant command in `docs/docker-tenants.md` on a capable disposable host before making any isolation claim.

Set `TENANT_DRIVER=docker`, `DOCKER_HOST=unix:///var/run/docker.sock`, `TENANT_REGION=local` and `TENANT_HOST_IMAGE=<reviewed preloaded repository@sha256:digest or local sha256:image-config-digest>` on the provisioner. Never give the socket or provider credentials to tenants. Keep `TENANT_DRIVER=fly` for production. If the owner accepts shared-kernel isolation for a separate deployment, document that risk acceptance and set `SWARM_ALLOW_DOCKER_TENANTS=1` explicitly when `NODE_ENV=production`. This does not approve Fly release gates or disable any containment checks.

Full Swarm host readiness additionally requires a compatible pinned image that passes the existing preflight under the restrictive Docker profile and a separately reviewed egress design to the owned platform/gateway HTTPS origins. The existing Fly host image is not qualified for this profile. The driver permits no external egress and does not attest local-volume encryption or disk quotas. Do not migrate customer accounts or run capacity growth through Docker until encrypted, quota-capable storage and the host/network boundaries have been implemented and reviewed. Never seed Fly evidence or weaken seccomp, capability drops, read-only roots, firewall rules or resource limits to satisfy these prerequisites.

## MT-D: Per-tenant meter ledger, logs and health

No new external account or secret is required to build or test MT-D. Actual collection needs the isolated platform and tenant hosts running after the existing owner-controlled infrastructure, credential and release-gate prerequisites are satisfied. This work does not run any external API, deploy a role, send a message or create qualification evidence.

1. Finish the approved staging bootstrap, including the dedicated Fly organization, restricted PostgreSQL serving connection, AWS KMS/S3, platform signing keys, Composio platform project and Google OAuth client. Use the existing runbook's exact credential names and callbacks. Do not substitute production credentials or bypass the qualification bootstrap dependency.
2. Run `server/dist/platform/migrate.js` as the dedicated migration role using `MIGRATION_DATABASE_URL`. Verify restricted serving-role DML grants include `tenant_meter`, `tenant_allowances`, `tenant_meter_resources` and `tenant_meter_status`. The serving roles must not receive schema-owner credentials.
3. Set the nonsecret environment value `TENANT_METERING=1` on the isolated platform and provisioner. Leave the shared standalone app unchanged. The provisioner passes this flag to new hosts and their tenant application; roll existing hosts to a reviewed image/configuration through the established qualified environment update process. Default unset or `0` disables report routes, collector scheduling and runtime allowance integration.
4. With a protected `/secure/directory-runtime.env` containing only the authorized restricted `DATABASE_URL`, run `node --env-file=/secure/directory-runtime.env server/dist/platform/meter-cli.js health`. Confirm real observations appear for the approved disposable tenants. No owner database credential belongs in a tenant container.
5. Allowances default to none. If an approved tenant should have a recurring USD soft allowance, run `node --env-file=/secure/directory-runtime.env server/dist/platform/meter-cli.js allowance --tenant <actual immutable tenant ID> --usd <approved positive USD amount>`. Use `--usd none` to remove it. Choose the amount as owner policy, not a fabricated default. This is a display-only allowance for tenant-reported known AI spend; it never enforces a lockout.
6. Choose a restricted log destination and retention/deletion policy before exporting logs or meter CSV files outside the operator environment. No destination, DNS record, webhook or alert delivery is configured by MT-D. Filter platform/provisioner/gateway request logs with the full `tenant_hash` from `health`; verify Docker driver label names from its separate runbook before selecting containers.
7. Qualify real provider lifecycle observations, long-gap behavior, clock synchronization, fleet polling capacity, tunnel/report freshness, export deletion and log redaction against approved disposable inventory. Local fakes and PostgreSQL tests do not establish real-provider billing completeness or satisfy a release gate. See `docs/tenant-operations-logs.md` for retention, source trust and observation limits.
