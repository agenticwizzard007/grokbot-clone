# Multi-tenant owner steps

## MT-A: Dockerized platform stack

Local Docker bootstrap requires no owner-held accounts or secrets. The following steps are required before using the same application image with real services; they were not executed by MT-A.

1. Provision a dedicated PostgreSQL database with `directory_owner` and `app_runtime` as in `infra/platform/staging-bootstrap.md`, sections 1 and 6a. Set `MIGRATION_DATABASE_URL` only on the one-shot job and `DATABASE_URL` only on trusted platform services. Use direct or session-pooled connections with TLS. Confirm runtime cannot create tables and receives LISTEN notifications.
2. Create the reviewed symmetric AWS KMS key and restricted principal using the AWS setup runbook. Set `TENANT_KMS_KEY_ID` to its ARN and `AWS_REGION` to its region. Supply AWS credentials through the SDK chain to platform, provisioner and gateway. Remove `TENANT_KMS_ENDPOINT` and all local emulator credentials. Prove generate/decrypt context restrictions with the real restricted principal before admission.
3. Create the private versioned backup bucket, prefix, lifecycle and incomplete-upload expiry policy. Set `BACKUP_BUCKET` and `BACKUP_PREFIX` on platform and provisioner. For AWS S3 omit endpoint overrides. For a reviewed Tigris or other S3-compatible service set `BACKUP_S3_ENDPOINT=https://<provider endpoint>`, `BACKUP_S3_REGION=<provider region>`, the provider's required `BACKUP_S3_FORCE_PATH_STYLE`, and separate `BACKUP_S3_ACCESS_KEY_ID`/`BACKUP_S3_SECRET_ACCESS_KEY` (optional `BACKUP_S3_SESSION_TOKEN`). Production overrides also require the deliberate setting `SWARM_ALLOW_LOCAL_CLOUD=1`. Never place object storage credentials in the AWS variables used for KMS. Qualify version deletion, multipart abort and restricted-prefix access with the real provider.
4. Generate a separate production Ed25519 pair offline with `scripts/platform-keys.sh /secure/swarm-production/keys`. Mount the private PEM only on platform at `PLATFORM_PRIVATE_KEY_FILE`; mount the public PEM on platform and gateway at `PLATFORM_PUBLIC_KEY_FILE`. Fly file secrets require base64-encoded PEM input. Do not reuse local emulator keys or the local session secret.
5. Supply the dedicated Composio project credential and webhook secret to gateway, and configure the real project/callback ownership according to the platform runbook. Supply the Google OAuth client through `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` on platform; register exactly `${PLATFORM_URL}/api/auth/google/callback`. Set owned HTTPS platform/gateway origins and their required DNS/certificate records. Local Caddy certificates are development-only.
6. For Fly, provide the dedicated staging organization and scoped driver token, publish the qualified tenant host digest and archive real qualification evidence through the existing tooling. Use the same reviewed role-image digest for the platform, provisioner, gateway and migration job with their existing Fly manifests. Do not deploy the live shared-server manifest. Omit `SWARM_LOCAL_PROVISIONER_HOLD` in production; missing evidence must still refuse provisioning. A Docker tenant driver deployment must follow its own reviewed supervisor and socket boundary. MT-A grants no Docker socket access and does not qualify that boundary.
