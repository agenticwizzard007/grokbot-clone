# MT-E tenant isolation evidence

This is local application-boundary evidence, not a production isolation certificate or a release-gate receipt. The matrix tests known foreign identifiers and credential substitutions against the shared platform components. It cannot establish that every possible attack is impossible. No cross-tenant leak was found in these cases; MT-E changes tests and documentation only.

Run date: 2026-11-28. Environment: Linux x86_64, Node v24.22.1, PostgreSQL 16.15. The database was disposable, loopback-only, with a fresh random schema per PostgreSQL suite. No production database, tenant, credential or provider account was used.

## New two-tenant matrix

Every test name in this table is an exact subtest title in [tenant-cross-access.test.mts](../tests/tenant-cross-access.test.mts), under `MT-E two-tenant cross-access matrix`. A and B are created through the real platform OAuth start/callback, Directory identity and session paths. Only the OpenRouter exchange transport is fake. Cookie flags, distinct owners, single-use bootstrap exchange and wrong-tenant/wrong-machine refusal are also asserted in the parent setup.

The gateway uses the real provider wrapper, policy and PostgreSQL registry with in-process SDK method fakes. Composio and Inkbox signature verification use locally generated HMACs and the real verification code. KMS transport remembers each wrapped key's tenant, purpose and key ID and refuses mismatched context. WebSockets use loopback, event inboxes use separate in-memory SQLite databases, object storage is in memory, and Fly uses the existing FakeFly transport. Unexpected fetches fail the test; SDK version checks and telemetry receive local fake responses. No messages are sent.

## What this does not prove

The binding requirements remain [master spec section 3](tenant-isolation-master-spec.md#3-rules-every-agent-follows). Local fakes do not weaken or satisfy those requirements. The test explicitly asserts that its `release_gates` table stays empty.

| Unproven boundary | Why local evidence is insufficient | Required workstream or release gate |
| --- | --- | --- |
| Real Fly network isolation | Loopback tunnels and fake inventory cannot prove separate private networks, metadata blocking, machine/volume ownership or cross-app reachability | WS4, `fly-network-isolation`, using two approved apps and the exact candidate image |
| Nested container containment | No nested host/container workload is booted here; no actual kernel, seccomp, sandbox, read-only root, capability, firewall or cgroup boundary is exercised | WS4, `nested-container-containment`; retain every security control during real qualification |
| Signed runtime bytes | The fixture image string has no published artifact, scan, signature or installed-byte attestation | WS1 and WS4, `signed-runtime-image` |
| Real KMS and IAM | Fake KMS verifies application context use, not AWS policy enforcement or principal selection | WS2 restricted-principal GenerateDataKey/Decrypt and wrong-purpose denial probe from the staging runbook; no separate named KMS gate in the master spec |
| Real S3, recovery time and erasure | In-memory objects and local recovery do not prove S3 IAM, durable/versioned deletion, key destruction, RPO or RTO | WS2 storage policy checks and WS7 real backup/restore/deletion drills; no separate named WS7 gate |
| Provider and OAuth behavior | SDK fakes and local signatures do not establish upstream account privacy, real identity verification, provider quotas, callback configuration, trigger schema compatibility or Inkbox delivery | WS5/WS6 feature/sign-up evidence; WS4 `provider-hosted-login` and `provider-quotas` |
| Routine execution and wake completion | Tests prove event ownership, B-only queued wake and inbox admission. Apply callbacks record effects; they do not run a routine, start an actual machine or prove scheduling latency | WS5 feature parity and WS6 routing, after WS4 qualification |
| Real deletion reconciliation | New deletion case uses fake apps/volumes with no running machines and marks simulated provider cleanup complete before the lifecycle tick. Existing tests cover fencing/races with fakes | WS6 account deletion and WS7 real cleanup drills |
| Deployment, capacity, monitoring and independent review | A real PostgreSQL test proves query/transaction behavior, not restricted production roles, LISTEN under real load, aggregate isolation capacity, alert delivery or exhaustive security | WS3 restricted-role/LISTEN smoke, WS8 monitoring, WS10 capacity and WS11 independent assessment; optional `tenant-capacity-resize` gate for real resizing |

No new feature flag is introduced. All new behavior is test-only. Existing host-usage opt-in is enabled only in the test fixture; deployment defaults and standalone code are unchanged. Owner-only qualification prerequisites and the unresolved initial staging bootstrap are listed in [MT-E owner steps](multitenant-owner-steps.md#mt-e-tenant-isolation-proof-matrix).
