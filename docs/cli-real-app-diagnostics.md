# CLI app approval diagnosis, readiness round 4

The failure on 6f67222 is reproducible with the installed Codex 0.167.1 binary, the real bridge argument construction, its real authenticated Swarm MCP endpoint, and an offline Responses model fixture. No ChatGPT login or live app account is used.

Codex lists the tools correctly, then returns `MCP tool call requires approval, but approval policy is never` to the model. No Swarm callback runs. The old `default_tools_approval_mode="auto"` asks Codex to decide whether the unannotated MCP tool needs its own approval. With `approval_policy="never"`, that request is rejected before the application can create its approval card. The earlier executable fixtures called MCP directly and therefore missed this gate.

The bridge now uses `default_tools_approval_mode="approve"` only for the per-generation `swarm` server and its exact manifest. This authorizes delegation to the existing Swarm dispatcher. It does not authorize an app action: account scope, schema, revision, saved blocked policies, durable approvals, denial and replay protection still run there. The read-only sandbox, never policy, disabled local tools, isolated environment, and required authenticated MCP server remain. Do not fix this by labeling write tools read-only or by bypassing Swarm approvals.

## Findings and evidence

| Check | Result |
| --- | --- |
| MCP names and filtering | `tools/list` uses raw case-sensitive names. Codex presents them in the `mcp__swarm` namespace with names such as `SWARM_APPS_SEARCH`, `SWARM_APPS_EXECUTE`, `tool_search`, `tool_describe`, and `tool_call`. A Responses function call uses `namespace: "mcp__swarm"` and the raw name. Claude uses `mcp__swarm__NAME`. Real-binary tests preserve case and a 64-character raw name. |
| Direct Gmail slug | `GMAIL_CREATE_EMAIL_DRAFT` is a Composio action slug, not a registered MCP tool. A raw call is rejected as unsupported. The supported route discovers it with `SWARM_APPS_SEARCH` and supplies it as `tool_slug` to `SWARM_APPS_EXECUTE`. Calling that wrapper directly also reaches the same approval checks. |
| Codex approval gate | The negative control restores `auto` in the test wrapper and reproduces the exact rejection. The fixed arguments deliver pending approval to the real binary and then to the mock model. The MCP server supplies no misleading read-only annotations and advertises no elicitation capability. |
| Deferred actions | Discovered app operations remain parameters of the registered execute wrapper. Deferred custom MCP tools use `tool_search`, `tool_describe`, and `tool_call`, including schema hash validation and the underlying approval policy. They do not expand the native manifest or bypass `nativeToolSession`. Real tests exercise both paths and denial. |
| Bot assignment and identity | There is no per-Bot Gmail enablement flag. Normal private Bot turns share account-scoped Composio tools. API and CLI use `connectionsDetail(userId)` and `executeComposio(userId, ...)`; standalone lookup uses private `userIds: [userId]`, and execution passes that same user ID. Tenant calls use the same gateway. Tests start fresh Bots without assignments and assert the identity on approved execution. Custom MCP assignment and group/setup restrictions remain separate. |
| Timeout and required startup | Zero generation timeout still gives each tool 900 seconds. Finite turns use the configured bounded tool timeout. A real one-second timeout produces a tool timeout result. With `required=true`, a wrong MCP bearer token prevents model inference entirely. |
| MCP auth | A random 32-byte token and loopback port belong to one generation. The token has no wall-clock expiry during that turn; closing/cancelling the generation closes its server. Host, origin and bearer checks remain. Hosted account credential homes and companion pairing authentication are separate from this MCP capability. |
| Claude Code | Installed 2.1.322 runs offline with a local Anthropic endpoint and dummy token. Its existing `dontAsk` plus exact `--allowedTools` registration works. No production Claude permission change was needed. |

## Customer guidance and logs

New failures use observed facts. A known inactive Gmail account gets a reconnect explanation and the real Connect card. A failed status lookup says the provider did not return the status and directs the customer to Connected apps, without claiming disconnection. A Codex MCP approval rejection produces a deterministic explanation and directs the customer to update Swarm or reconnect the computer bridge in Settings > Subscriptions. Model instructions require the actual failure and recovery step, and forbid vague access-restoration claims or pending approval without a real approval ID. Existing chat rows are not rewritten; a regression asserts this.

Server logs prefixed `[cli-generation]` contain a generation ID, provider, runtime, Bot/job IDs, manifest count and SHA-256 of sorted names. Tool records contain the wrapper name, app action slug when applicable, admission/result classification, stopped state, and error class. They never include arguments, message bodies, tokens, provider response bodies or exception text. Codex rejections before the server callback are extracted as bounded classifications from real CLI events and returned by the runner. This distinguishes an empty/changed manifest, no attempted call, local CLI rejection, Swarm admission refusal, pending approval and transport failure in Fly logs.

## Reproduction and validation

Run `npm run test:cli-real-apps`. The fixture resolves binaries through each installed package's `package.json` bin field, as hosted.ts does. Test-only executable wrappers stub subscription status and Claude's account catalog because those require a real subscription. Generation always launches the installed binary with the bridge's actual arguments. The only added settings select a loopback mock model provider and dummy credentials; negative controls explicitly override the MCP approval mode, token or timeout. Production cannot select these test providers.

The tests cover Codex and Claude, hosted and WebSocket companion transports, direct wrapper calls, app search/execute, described tool_call, deferred custom MCP tools, durable approval rows, main-chat SSE, pending results returned through the official CLI, voice delegation, allow-once identity, denial, stale replay, missing/expired/unavailable/blocked accounts, legacy name rejection, manifest limits, required startup and tool timeout. Local Playwright uses the real binaries at 1280 and 390 pixels in light and dark, checking the card, 16 body lines, denial, reload and overflow. No live app login or real user data is involved.

An existing companion installation must download/restart the updated bridge to get the corrected Codex arguments. Hosted generations use the deployed bridge. The mock model proves tool reachability and approval behavior, but cannot establish a live language model's routing choices or external Gmail availability. The deployment revision is verified separately after merge.
