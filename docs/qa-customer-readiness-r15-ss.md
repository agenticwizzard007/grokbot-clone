# R15 stream SS: voice call start feedback

R15-2 is reproducible in the start controls. Composer and Voice Settings treated both `connecting` and `live` as an active call, so the next click could call `endCall()` during setup. `start()` already set connecting before its first await, but the AudioContext constructor ran first. The new controller regression observes idle during construction on untouched ddc9128. The browser regression also fails there because the composer start button remains enabled while connecting.

`startCall()` now reserves connecting synchronously before browser audio construction and ignores further starts during setup. Composer shows a disabled progress icon with the accessible label Connecting, and the call bar shows Connecting or Waiting for microphone permission. Voice Settings shows a disabled Connecting button. More actions shows Connecting and ignores another selection, including with a saved draft. Handlers read current state so events queued before a React render cannot cancel setup. The permission message wraps at phone widths.

Only live calls expose End and mute. The call bar retains a separate Cancel button during setup because a browser permission prompt has no deadline. This preserves an intentional way to leave a pending request without making the original Start control a toggle. Failure keeps its explanation and Retry. Live behavior, chat work, approvals, mute and End retain their existing paths.

No fixed 10-second success-path stall was reproduced locally. Browser audio resumes in the user gesture, microphone permission is awaited, audio capture starts, the session token is fetched, and the realtime WebSocket handshake completes. The existing 10-second deadline begins after microphone permission and covers all remaining stages. A controlled successful setup reaches live without advancing timers. Held audio, token and handshake fixtures retain visible progress and fail with the existing actionable errors. No deadline or provider behavior was changed.
