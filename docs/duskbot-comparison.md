# Duskbot → Swarms: what to adopt, what to leave alone

**Recommendation:** ship a safe, account-scoped **Support Snapshot** first. Then make **Needs You** the first substantial product investment: a live view of the few decisions only the owner can resolve, linking back to the original task or card. Swarms already has a chief of staff, durable work, outputs, and recovery boundaries. Duskbot's advantage worth adapting is how it makes those systems legible to the person supervising them—not a reason to replace them.

**Basis:** read-only source review on November 19, 2026. Live Swarms `origin/main` was [`46ffb7cc090ea70e179c9f6511a7e57f9f187311`][sw-commit]; Duskbot's public default `main` and its GitHub parent's `main` both pointed to [`a325fb5b66516f153dfa679fe50802d7f95bade7`][du-commit]. “Shipped” here means in that verified Swarms main tree, not that every hosted gate is enabled or every production environment was exercised. Tests below are repository evidence, not results from this review. See [evidence and commit manifest](duskbot-comparison-evidence.md).

## 1. What Duskbot actually is

- **Own-your-runtime assistant, with real team/cloud breadth.** The Electron/React desktop app connects to a Node workspace server on the same computer, a self-hosted machine, or a managed home. The server runs engine adapters, chats, app and computer tools, cards, routines and the vault; remote connectivity is a separate link layer. Chats are in SQLite and bot state is rooted in the machine's data directory. The managed control service provisions and identifies machines separately from their runtime. This is desktop-first, not personal-only. [Architecture][du-arch] · [Managed service][du-cloud]
- **Collaboration is wired, not a mock.** Duskbot's coordinator creates durable, parent-linked `Assignment` records with an event trail and wake inbox. Work, consultation, one-way notices and human answers are separate modes. A room/solo goal run drives bounded coordinator/worker turns; it can stop on an invalid decision, a repeated brief or its turn limit. It isn't the same contract as Swarms' long-lived goals with evidence and dependency-aware workflows. [Coordinator wiring][du-coord] · [Assignment types][du-types] · [SQLite store][du-store] · [Goal runner][du-goal] · [Fake-runner scenarios][du-scenarios]
- **Team Cloud has explicit sharing and governance.** Bot access and conversation visibility are distinct; member-private conversations aren't just a visual filter. The source has viewer/audience checks, signed managed policy, and tests asserting that owners/admins cannot read, mutate, stream, or extract a member's private thread through the bot. Shared bot and team-owned AI/app connections coexist with personal paths. The docs also enumerate gaps, e.g. no per-member saved logins and no member-owned team engine sign-in. Swarms' primary hosted boundary is the immutable account and its isolated runtime, not an equivalent nested Team Cloud role system. [Visibility code][du-visibility] · [Signed policy][du-policy] · [Privacy tests][du-private] · [Documented limits][du-team-limits] · [Swarms tenant architecture][sw-tenant]
- **Operating unattended gets substantial product attention.** The code aggregates actionable exceptions, posts routine results into the appropriate conversation, leaves a receipt for quiet outcomes, and handles failure causes differently. Routines support schedules/events and limited catch-up; deterministic checks can run without starting a full agent job. Not every engine or workspace gets the same proactive experience: the personal watch/brief is explicitly excluded from hosted teams, and the v1 verification notes include fixture-backed connector behavior. [Needs You route][du-attention-route] · [Run reports][du-report] · [Scheduler][du-schedule] · [No-AI checks][du-checks] · [Proactivity limitations][du-watch]
- **Meaningful implementation, uneven qualification.** `package.json` and the checked-in signed release index say **0.2.23**; the README badge still says **0.2.13**. Source and regression harnesses support the runtime, team privacy and dashboard claims, but do not establish live reliability, platform parity, or exact-once writes. The phone audit explicitly lists unverified physical-device behavior. The “unified provider handling” document is a proposal, not a shipped single engine. [Version][du-version] · [Release index][du-release] · [README badge][du-badge] · [Mobile audit][du-mobile] · [Provider proposal][du-provider-proposal]

**Provenance / reuse.** The inspected GitHub fork names `DuskBotAI/duskbot` as parent; Swarms names `nickvasilescu/orgo-teammates`. An exact reachable-commit intersection on both non-shallow histories returned zero. That rules out a shared Git ancestor at these pins, not borrowed ideas or imported/squashed material. Duskbot credits OpenMausBot and documents an Apache-2.0 carveout for **original** OpenMausBot code, not the Duskbot modifications. Its Grok Bot import is an interoperability path, not ancestry; notices credit the Hermes plugin for the import approach. The pinned Duskbot work and fork changes are identified as **PolyForm Noncommercial 1.0.0**. Translate behavior and specs independently. Don't copy Duskbot code, UI assets or changes into commercial Swarms without confirmed rights; if considering original OpenMausBot code later, verify the exact upstream revision plus notices separately. ## 2. Where the two products differ in practice

| Area | Duskbot's implemented behavior | What Swarms already ships; what is actually missing |
|---|---|---|
| **Team work, goals, and lineage** | A single assignment tree records origin, requester, destination, outcome and observed evidence. Bounded room goal runs are easy to kick off in chat. [Types][du-types] · [Goal runner][du-goal] | Swarms already persists owner-scoped internal requests with idempotency, parent context, admission and job outcomes; it exposes per-agent exchange histories. Native goals verify evidence; workflows schedule dependency-ready tasks and enforce budgets. Keep these richer contracts. Improve how a person sees what is blocked, where it originated and who can act. [Requests][sw-requests] · [Exchanges][sw-exchanges] · [Goal evidence][sw-goal] · [Workflow scheduling][sw-workflow] · [Workflow budgets][sw-budget] |
| **Daily accountability vs immediate action** | `GET /api/needs-you` projects viewer-visible open asks/operational blockers; the frontend fetches it. It deduplicates repeated asks and clears recovered problems. Some causes are derived from tool/output text; the broader Today report estimates time saved using heuristics. Borrow the interaction, not those inference rules or implied ROI. [Route][du-attention-route] · [Projection][du-attention] · [Client][du-attention-client] · [Tests][du-attention-tests] · [Time estimate][du-minutes] | Swarms already has chat cards, sidebar indicators, Team Board next steps/health and a daily, source-backed Quinn synopsis. It does not need a second daily reporting system. No cross-bot owner action queue built from currently actionable records was found in the inspected web paths. [Chat cards][sw-cards] · [Team Board][sw-board] · [Team state][sw-state] · [Synopsis coverage][sw-reports] |
| **Routines and uncertainty** | Cause-specific attention, bounded quota/busy waits and some retries/fallbacks, catch-up/missed receipts, and quiet/reporting destinations. The generic retry prompt asks the model to check prior effects; it is not proof an effect did not occur. [Classification][du-recovery] · [Wait/retry][du-retry] · [Scheduler][du-schedule] · [Report delivery][du-report] | Swarms already has durable fire-key/overlap checks, job lineage through approvals/questions, immutable outputs and separately reconciled deliveries. It deliberately records `unknown` rather than replaying after owner loss. Daily synopsis already has durable slot catch-up and quiet hours; ordinary cron in `routines.ts` installs callbacks without equivalent missed-window catch-up. Browser recovery already bounds actions and offers a human checkpoint; its watcher is current-turn/process only. Enrich status first, preserve `unknown`, and avoid conflating cron, browser and delivery recovery. [Schedule][sw-routine] · [Run recovery][sw-routine-recovery] · [Synopsis scheduling][sw-synopsis-slots] · [Browser boundary][sw-browser] · [Existing tests][sw-run-tests] |
| **Outputs in the review loop** | Attachments can open bounded Markdown/text/PDF and HTML previews; HTML has an empty sandbox and a restrictive CSP; delimited tables have a bounded read and worker parser. [File preview][du-preview] · [Frame][du-frame] · [Table preview][du-table] | Web Routine History and Library provide downloads. Swarms already protects artifact ownership and integrity and deliberately responds as an attachment. Add a separate, safe review path for the immutable artifact rather than weakening download headers or inventing another artifact backend. [Routine History][sw-history] · [Library][sw-library] · [Artifact access][sw-artifacts] · [Download headers][sw-download] |
| **Memory, procedures and agent evolution** | Readable bot memory and hybrid recall over scoped facts. The implementation combines lexical candidates and optional vectors; docs distinguish editable files and the fact store. [Recall][du-memory-code] · [Memory docs][du-memory] | Swarms already has ownership-scoped, evidence-backed memory correction/forgetting, skill revisions, evaluations and append-only agent change history. A folder-based memory migration is not an upgrade. If recall quality becomes a priority, use a cited retrieval benchmark rather than assuming vectors improve it. [Memory][sw-memory] · [Evolution contract][sw-evolution] · [Evolution tests][sw-evolution-tests] |
| **Engine/approval and tenancy boundaries** | Driver support and a reset-to-Ask check for incompatible engine/custom permission changes; some local defaults are broader and Chief lineage can raise a child's level. Personal cloud and team sharing have a different trust model. [Compatibility][du-compat] · [Delegated level][du-level] | Swarms already connects Codex/Claude subscription routes and API modes, keeps account credentials isolated and retains the selected subscription mode on reset/disconnect so it does not silently bill APIs. Its turn loop binds approvals to exact calls and fences dispatch. Document/enforce capability parity at the boundary; never inherit broader authority or replace account isolation. [CLI architecture][sw-cli-doc] · [Reset/disconnect][sw-cli-reset] · [Dispatch approval][sw-approval] · [Runtime identity][sw-identity] |

## 3. Ranked adoptions

Effort: **S** = one bounded server/client slice; **M** = multiple existing surfaces or lifecycle integration; **L** = new policy/portable state and broader qualification. Risks below are residual implementation risks, not forecasts. Ranking weights user value, tractability, and safety, not novelty.

| Rank and lesson | User journey and value | Effort / risk / prerequisite |
|---|---|---|
| **1. Support Snapshot** — Duskbot makes diagnostics discoverable from Settings. [UI][du-diag-ui] · [Implementation][du-diag] | Nia's scheduled report stops after the selected subscription expires. The owner opens Settings → Support Snapshot, sees **sign-in required** with freshness and an existing reauth link, previews the exact safe JSON and chooses whether to download/share. No support round-trip to determine build, runtime or provider health. | **High value, S, low–medium privacy risk.** Reuse version, cached CLI status and bounded health/outcome data. Define an allowlist first; export no raw logs. [Version][sw-version] · [CLI status][sw-cli-status] · [Health][sw-state] |
| **2. Needs You for Quinn** — edge-triggered attention in one place. [Dusk filters][du-attention] | Quinn delegated work to Nia and another coworker. The owner sees two pending decisions, opens the original card by agent and message, resolves it there and sees the item disappear. The synopsis is still the recap; this is today's actionable queue. | **High, M, medium.** Start with authoritative pending approval/question records and known ownership/generation. Later add typed setup/connection issues; no transcript mining or parallel action endpoint. [Existing answer routes][sw-answer] · [Existing cards][sw-cards] |
| **3. Preview the deliverable in place** — bounded, inert inspection. [File preview][du-preview] · [Tables][du-table] | While reviewing Nia's weekly report, the owner reads Markdown or scans a small CSV beside the run, then follows the existing review/approval path for the same artifact. Less download friction; no preview itself signals acceptance. | **High, M, medium content-safety risk.** Reuse immutable artifact IDs/ownership. Start with text/Markdown and only then bounded CSV/TSV. Defer HTML/PDF and data dashboards. [Artifact store][sw-artifacts] · [Existing download][sw-download] |
| **4. Give routine failures useful next steps** — surface cause, recovery state, and actual outcome. [Dusk cause taxonomy][du-recovery] · [Report routing][du-report] | The owner can distinguish **waiting for usage reset**, **couldn't verify prior send**, **not run during downtime**, and **nothing to report**. A clear route to the existing action beats repeated failed notifications. Later, one opted-in read-only routine can coalesce missed slots instead of flooding the owner. | **High, M for status / L for safe catch-up; medium / high.** Need stable cause codes, fire keys and a defined safe subset. Preserve unknown, cap retry/backoff, and no billing-mode changes. [Existing run state][sw-routine-recovery] · [Existing slot model][sw-synopsis-slots] |
| **5. Rehearse a routine before enabling it** — Duskbot has a manual `dryRun` flag and an outbound connector guard, but that is not evidence that every provider, shell, browser and native MCP path is side-effect-free. [Flag][du-dry-run] · [Connector guard][du-dry-guard] | Quinn sets up “summarize new sales leads each Monday.” The owner sees the schedule, allowed sources and proposed output/destination, and can run one supported read-only rehearsal without posting or changing the schedule. | **Medium–high, M for static preview; L for live rehearsal, high.** First validate and render a plan with zero model/network/tool calls. A live preview requires a server-side allowlist on every callable surface and no direct provider/local escape path. Reuse existing delivery preview for destination confirmation. [Delivery preview][sw-delivery-preview] |
| **6. Show effective tool permissions by mode/provider** — distinguish a consultation from work, and label unsupported permissions before engine changes. [Modes][du-types] · [Dusk compatibility][du-compat] | Quinn asks a specialist to advise on a draft; the owner sees **can read, cannot send**. Switching the specialist from one subscription runner to another never broadens the grant; unsupported operations are explained, not silently routed. | **Medium–high, M for capability UI; L if adding consult enforcement, high.** Derive from registered tool contracts; apply whichever existing or requested scope is stricter. Qualify API and CLI callback parity before advertising read-only execution. [Tool schemas][sw-tools] · [Native loop gate][sw-native-gate] |
| **7. Portable team blueprints, not live moves** — Duskbot has a versioned team manifest and an import/review model. [Manifest][du-manifest] · [Team sharing rules][du-sharing] | An owner reuses a reviewed Quinn + analyst setup in a new account. A preview lists roles and unmapped connections; imported schedules remain off and nothing sends until explicitly enabled. Do not confuse this with an account transfer or backup restore. | **Medium, L, high data/permission risk.** Swarms already replicates one teammate. Do blueprints only after demand is proven; build on its manifest with a stricter configuration-only export that drops source conversation text and all live state. [Swarms manifest and replicate][sw-replicate] |

## 4. Phased implementation proposal

**Phase 1 — first bounded PR: Support Snapshot (S).** Add an authenticated account-runtime `GET /api/support/snapshot` (new route mounted in `server/src/tenant-app.ts`) and a Settings panel near `web/src/components/config/SubscriptionSettings.tsx`. Build a small typed DTO, not a dump of `teamState()`, CLI payloads, or logs. Allow only: app revision, observation time, selected provider family and billing-mode enum, cached installed/authorized/readiness enums, supervisor observation/freshness, and bounded aggregate routine outcome counts from owned rows. Treat an unavailable or old observation distinctly from a failed or healthy check. Show plain-language next steps through existing links; the download contains the previewed JSON and is explicitly user-triggered. No reconnect, model, provider refresh, background watcher, auto-upload, global operator state, native change or schema migration. Exclude names/IDs, email, prompts, paths, tool arguments, credentials, account/provider text, and arbitrary error strings. Proposed `Cache-Control: private, no-store`. **Acceptance/tests:** account A cannot retrieve B's status or counts (including guessed IDs and wrong runtime/expired session); inject canary strings into provider errors, tool payloads and agent titles and assert no output leakage; staleness and missing data stay truthful; loading/error/preview/download tested in existing web harness style with providers stubbed; verify byte equality between displayed DTO and download. Existing version, owner-scoped CLI and health code are starting points, not the response schema. [Mount points][sw-mounts] · [Auth][sw-auth] · [CLI auth/isolation tests][sw-cli-tests]

**Phase 2 — reduce supervision friction (two separate M slices).** First add a read-only `/api/team/attention` projection next to `server/src/routes-coordination.ts`, using `server/src/coordination/` for canonical open approval/question queries, current bot generation/visibility, bounded pagination, and stable IDs for deduplication. Put an entry point in the web shell/Team Board; use existing SSE/refresh and cards for navigation and resolution. An old approval must not keep counting after expiry/answer, restart, bot reset, or revoked access; an answer from another tab clears promptly; cached results must never carry across account switch. Exercise concurrent answers, duplicate representation of one request, foreign bot/generation, resolved and cancelled cards, SSE reconnect, accessible desktop/mobile navigation. For the separate preview slice, add an authenticated, byte-limited text preview to `routes-deliverables.ts`/`deliverables/artifacts.ts` and reuse it from Routine History and Deliverables. Preserve immutable-byte checks and attachment behavior; render text inertly, disable raw HTML and remote loads in Markdown, show size/truncation, keep full download as a fallback. Golden tests: hostile HTML/Markdown, malformed encoding, oversized files, abort, safe foreign-ID failure, exact historical version, and no change to approval or delivery status. Add bounded CSV only after this, with row/column limits and a responsive parser. [State and routes][sw-coord-route] · [Run history][sw-history] · [Artifact tests][sw-run-tests]

**Phase 3 — safer routine operation (M for reporting/static validation; L for optional execution changes).** Extend `deliverables/runs.ts`/`types.ts`, `routines.ts` and `RoutineHistory.tsx` with typed observed outcomes (including unknown, missed, waiting on owner and skipped by policy), reasons, and safe next actions. Labels like “waiting until 09:00” require an actual scheduled recheck; do not fabricate a retry time. Add the static schedule/source/destination rehearsal in the existing routine UI; no calls are dispatched. Only after that, and only with opt-in and proven safe operations, trial bounded missed-window catch-up for ordinary cron with a persisted cursor and existing fire-key admission. When safe read-only status or effect idempotency cannot be verified, fail closed and require review; never retry `unknown` generically, rerun an uncertain delivery, or select a paid fallback. Tests: time jumps/DST, held/migrating tenants, crash between claim and dispatch, duplicate workers, usage cap and overlap, disabled/edited schedules, unavailable provider, and writes that succeeded remotely before acknowledgment. Run these with a fake clock and stubbed effects. [Ordinary cron][sw-routine] · [Synopsis as reference][sw-synopsis-slots] · [Existing unknown handling][sw-routine-recovery]

**Defer or avoid.** Follow with provider capability visibility only when it removes a measured mode-switch/support problem; wait on execution-enforced consult and team templates until isolation and demand justify them. Defer the user-facing vault: Duskbot really has encrypted saved secrets with metadata summaries, but hosted injection would need a separately reviewed destination/consent/secret-output design. Do not transplant Electron, relay/cloud installation plumbing, Team Cloud's same-audience rules or default full access, the assignment engine, broad automatic retry/fallback, or the file/backup model. Do not clone the personal watch feature wholesale. Build on Swarms' account identity, approval binding, and canonical evidence. [Saved secrets][du-vault] · [Approval defaults][du-default] · [Tenant boundaries][sw-tenant]

**Decision signals.** For the snapshot: track only reason-code coverage and whether users can identify a next step without exposing the payload to telemetry. For Needs You: baseline time from open decision to resolution, share opened from the workspace queue, and stale/duplicate cards; a missing provider status must not become a false action item. For previews: track preview open→existing review action and errors by file type, not file contents. Establish baselines before setting numerical claims or resorting to a “time saved” heuristic.
